# T22 — Production alembic chain is stuck; create_all masks it

**Status:** resolved — all three sites at head, backfill applied
**Priority:** high
**Source:** [postmortem 2026-07-27](../postmortem-2026-07-27-thread-index-403.md)

## Confirmed on origin, 2026-07-28 (read-only)

| site | alembic `current` | behind head by |
|------|-------------------|----------------|
| `my.remarkbox.com` (`production.ini`) | `d47dc908d2ea` | 3 revisions |
| `foxhop.net` | `554e2329ebf0` | 1 revision |
| `westworld2.com` | *(no revision reported)* | unknown |

Our head is `df0217588814`. The chain runs:

```
7c624a8fae9e → d47dc908d2ea → 8e3c406e4049 → 554e2329ebf0 → df0217588814
                    ▲ my.remarkbox.com          ▲ foxhop.net    ▲ head
```

Schema inspection of `my.remarkbox.com.sqlite` (table names only):

```
rb_revision: True | rb_api_token: True | tables: 21
```

## Root cause

`rb_revision` is created by `8e3c406e4049` and `rb_api_token` by
`df0217588814`. Alembic says neither has been applied, yet **both tables
exist**. They were created by `Base.metadata.create_all()` — the
`initialize-database-for-{{ site }}` step salt runs immediately before
`alembic upgrade head` (`foxhop-states/uwsgi/sites.sls`).

So every deploy plays out like this:

1. `create_all` silently creates any table our models gained.
2. `alembic upgrade head` starts at `d47dc908d2ea` and tries `8e3c406e4049`,
   whose first act is `CREATE TABLE rb_revision`.
3. That table already exists, so the migration errors and the whole upgrade
   aborts.
4. Every later revision — including data migrations — never runs.

The schema therefore always *looks* correct, because `create_all` keeps it in
step with our models, while **data migrations silently never apply**. That is
what caused our 2026-07-27 outage: `554e2329ebf0` backfills
`rb_namespace.public` to `True`, it never ran, and enabling enforcement took
every thread index to 403.

The sites disagreeing with each other is what an aborting chain looks like
over time: `foxhop.net` got as far as our backfill, `my.remarkbox.com` did not.

## Fix — migrations made idempotent

Rather than hand-repairing production with `stamp`, our migrations now
tolerate meeting a table `create_all` built first.
`remarkbox/lib/migration_helpers.py` provides
`create_table_if_missing` / `create_index_if_missing` (and drop equivalents),
and the two blocking revisions — `8e3c406e4049` (`rb_revision`) and
`df0217588814` (`rb_api_token`) — now use them.

Because salt already runs `alembic upgrade head` on every release, this
repairs itself: our next deploy walks `d47dc908d2ea` → `8e3c406e4049` (skips
the existing table, stamps) → `554e2329ebf0` (**runs our backfill for real**)
→ `df0217588814` (skips, stamps) → head. No manual production writes.

This is better than stamping. Stamping asserts "this already happened" and
would have hidden the same drift again on our next new table; a guard makes
the migration honest about what it found.

### Verified against a reproduction, not just in theory

A copy of our development database was put into production's exact state —
every table present, `alembic_version` set to `d47dc908d2ea`, and all 11,917
namespaces forced to `public = 0`:

```
before:  sqlite3.OperationalError: table rb_revision already exists
after:   alembic_version = df0217588814
         public distribution = [(1, 11917)]
```

`remarkbox/tests/test_migration_helpers.py` pins the behaviour, including that
running a whole migration twice is safe.

### Confirmed on origin after deploy `28c444d`

```
production.ini      => df0217588814 (head)
foxhop.net.ini      => df0217588814 (head)
westworld2.com.ini  => df0217588814 (head)

public distribution: [(1, 23874)]
```

All three sites caught themselves up on the deploy, with no manual database
writes. Every one of production's 23,874 namespaces now reads `public = 1`,
so no row is left in the state that caused our outage.

`westworld2.com` turned out to be at `d47dc908d2ea` like our main site — our
first read of it reported nothing only because the output was truncated, not
because its chain was unstamped.

## Systemic fixes worth making

1. **Take `create_all` out of our deploy path.** It is what hides the broken
   chain. A missing table should fail loudly rather than be conjured behind
   alembic's back.
2. **Fail the deploy when `alembic upgrade head` errors.** A release currently
   goes live with its migrations aborted and nothing says so.
3. **Report migration state somewhere we look.** Three sites silently
   disagreeing about their schema version should be visible before it causes
   an outage, not after.
