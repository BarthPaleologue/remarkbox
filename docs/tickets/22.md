# T22 — Production alembic chain has not applied our backfill

**Status:** open
**Priority:** high
**Source:** [postmortem 2026-07-27](../postmortem-2026-07-27-thread-index-403.md)

## Problem

Migration `554e2329ebf0` backfills `rb_namespace.public` to `True`. Production
behaviour proves it has **not** applied: enabling enforcement took every thread
index to 403, which only happens when rows still read `False`.

Yet `rb_api_token` exists on production, and that table belongs to
`df0217588814`, a *later* revision. Both cannot be true of a healthy alembic
chain.

## Likely explanation

Salt runs `initialize-database-for-{{ site }}` — which calls
`Base.metadata.create_all()` — immediately before `alembic upgrade head`
(`foxhop-states/uwsgi/sites.sls`). `create_all` builds missing tables straight
from our models and knows nothing about alembic. So our token table can appear
while the alembic chain is stalled or erroring at some earlier revision.

If so, **schema changes reach production while data migrations silently do
not** — a general correctness problem, not one feature's problem.

## Investigate

```bash
# On origin.remarkbox.com, read-only:
/opt/remarkbox/env/bin/alembic -c /opt/remarkbox/my.remarkbox.com.ini current
/opt/remarkbox/env/bin/alembic -c /opt/remarkbox/my.remarkbox.com.ini history | head
```

Compare `current` against our local head. If it is behind, find the revision
that errors and why. Salt's last highstate output for
`alembic-upgrade-head-for-my.remarkbox.com` should carry the failure.

## Fix, in order

1. Repair the chain so `alembic upgrade head` completes.
2. Confirm no namespace reads `public = 0` afterwards.
3. Only then re-enable `namespace.enforce_private_lists`.
4. Decide whether `create_all` should stay in our deploy path — masking a
   failing migration chain is worse than failing loudly.
5. Decide whether a failed `alembic upgrade head` should fail our deploy.
