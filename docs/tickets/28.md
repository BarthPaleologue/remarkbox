# T28 — Browser and embed posts bypass spam scoring entirely

**Status:** open — needs a decision from fox before any code
**Priority:** high
**Source:** found while building [T27](27.md) telemetry, 2026-08-31

## What is true today

`score_content` has exactly one caller in our whole codebase:
`remarkbox/api/views.py`. Our browser post handlers do not use it.

`remarkbox/views/new_thread.py:32` and `remarkbox/views/reply_node.py:38`
both do:

```python
if request.spam:
    return request.spam
```

`request.spam` is our whole browser defence (`remarkbox/__init__.py:454`):

```python
def add_spam(request):
    """Test if request looks spammy HTTP Error or False."""
    if request.params.get("email2", "") != "":
        # spam filter, hidden email2 field tricks bots.
        return HTTPUnauthorized("you smell like a spammer")
    return False
```

A hidden honeypot field. Nothing else. No `score_content`, no link density,
no IP reputation, no duplicate detection, no LLM relevance check, no
thresholds.

| post route | honeypot | scoring | LLM relevance |
|------------|----------|---------|---------------|
| `POST /api/v1/threads` | — | yes | yes |
| `POST /api/v1/threads/{id}/replies` | — | yes | yes |
| browser new thread | `email2` only | no | no |
| browser / embed reply | `email2` only | no | no |

Verified by sweep: no tween applies scoring (`__init__.py` registers only
rate limiting and CSRF tweens), and `models.spam` has exactly one importer.

## Why this matters

Our embedded comment widget is our main product surface, and it posts through
our browser path. Our spam pipeline we have been debugging all week guards our
API door while most traffic uses our front one. Any claim that our filter is
"working" is scoped to API posts only.

A honeypot stops naive bots. It does nothing against a headless browser, and
nothing at all against relevant-looking human spam, which is precisely what
our relevance check exists to catch.

## Why this is not already fixed

Turning scoring on for browser posts changes what happens to **real users'
comments**. At our current thresholds (`hard 0.8` reject, `soft 0.5` hold) a
false positive silently rejects a legitimate comment mid-conversation, or
holds it for a moderator who may never look. That is a product decision about
our tradeoff between spam and lost comments, not a defect to patch quietly.

It also adds a synchronous LLM call to our interactive comment path. Our
inference endpoint answered a canary in roughly a second during testing, with
`spam.llm.timeout` defaulting to 5s. That latency is acceptable on an API
write and questionable on a human pressing Reply.

## Options

1. **Telemetry first, enforcement later.** Score browser posts, record a
   `SpamEvent` with `source="browser"`, but take no action on our result.
   After a week we know our real false-positive rate before anything is
   blocked. `SpamEvent.source` already exists for exactly this.
2. **Hold, never reject.** Apply our soft threshold only, so a suspected post
   waits for a moderator instead of vanishing. Needs our namespace to have
   someone actually reading our moderation queue.
3. **Full parity with our API path.** Simplest to reason about, largest blast
   radius on real conversations.
4. **Async scoring.** Accept our comment immediately, score after, disable
   retroactively. Keeps our reply path fast; spam is briefly visible.

Recommend **1**, then decide between 2 and 4 with real numbers in hand.

## Prerequisite

[T27](27.md) telemetry must be deployed and collecting first, or we will be
choosing thresholds by guesswork.
