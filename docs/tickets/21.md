# T21 — demo.remarkbox.com fails TLS handshake

**Status:** open
**Priority:** medium
**Source:** noticed 2026-07-27 during post-deploy verification

## Symptom

```
$ curl -sv https://demo.remarkbox.com/
* Connected to demo.remarkbox.com (142.93.73.64) port 443
* TLSv1.3 (IN), TLS alert, internal error (592):
* OpenSSL/3.0.13: error:0A000438:SSL routines::tlsv1 alert internal error
```

curl reports `000` — no HTTP response at all. DNS is fine: `demo.remarkbox.com`
resolves to `142.93.73.64`, our edge proxy, same as `meta` and `faq`, which
both serve 200.

## Not related to our 2026-07-27 outage

Found while verifying recovery from
[our thread-index 403 outage](../postmortem-2026-07-27-thread-index-403.md).
It is unrelated: that outage was an application-level 403 from our own code,
and no Python change can cause a TLS handshake alert at our edge. `demo` was
already failing this way while `meta` and `faq` were serving normally.

## Likely cause

Our proxy cannot present a certificate for this hostname. That is the same
shape as our 2026-02-25 SSL outage
([postmortem](../postmortem-2026-02-25-ssl-outage-caddy-acme.md)): a CNAME
domain without an explicit Caddy block falls through to on-demand TLS and
fails. `demo` is listed as live in our routing map in `CLAUDE.md`, so either
its block is missing from `~/git/proxy.unturf.com/ingress/Caddyfile` or its
ACME issuance is failing.

## Next steps

1. Check for a `demo.remarkbox.com` block on our edge proxy Caddyfile.
2. Check Caddy's ACME logs on `proxy.unturf.com` for issuance failures.
3. If `demo` is meant to be retired, remove it from our routing map in
   `CLAUDE.md` so it stops reading as live.
