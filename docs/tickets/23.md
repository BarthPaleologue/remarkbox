# T23 — pkg_resources under setuptools>=81

**Status:** resolved — vendored shim already handles it; no pin needed
**Priority:** medium
**Source:** noticed 2026-07-28 while diagnosing [T22](22.md)

## What I saw

On origin, inside our deployed virtualenv:

```
$ env/bin/pip show setuptools
Version: 82.0.1
$ env/bin/python -c "from pyramid.paster import get_appsettings"
ModuleNotFoundError: No module named 'pkg_resources'
```

setuptools 81 removed `pkg_resources`, and `pyramid.asset` / `pyramid.path`
(pyramid 2.0.2) still import it.

## What was actually true

This was already solved before I filed the ticket, and my first fix made
things worse rather than better.

1. **Our theme loading never used `pkg_resources`.** `load_entry_points`
   (`remarkbox/__init__.py:150`) uses `importlib.metadata.entry_points`, which
   is stdlib. Themes carry no setuptools coupling at all.
2. **Pyramid's use is covered by a vendored shim.** Commit `112d3fd` added
   `remarkbox/_vendor/pkg_resources/__init__.py` — a small stdlib-backed
   implementation of the six functions pyramid touches — and
   `remarkbox/__init__.py` puts `_vendor` on `sys.path` *before* importing
   pyramid.

Verified by simulating setuptools>=81 (blocking the real module through a
`MetaPathFinder`) and importing our package:

```
pre-remarkbox import blocked as intended
after remarkbox, pkg_resources -> remarkbox/_vendor/pkg_resources/__init__.py
is our vendored shim: True
pyramid.paster OK: True
```

That is why production serves normally on setuptools 82.0.1: uwsgi enters
through the `remarkbox:main` paste factory, so our package — and therefore our
shim — is imported first.

## Correcting my own fix

I first pinned `setuptools<81` in `requirements.py3.txt` and regenerated the
lock. That was redundant, and worse: it holds a build tool back to keep a
deprecated API alive, which is exactly what vendoring exists to avoid.
Reverted.

The diagnostic that started this was also flawed — it imported
`pyramid.paster` **without** importing `remarkbox` first, so the shim was never
installed. The failure was in my command, not in the deployment.

## Genuinely remaining, and narrow

Anything that imports pyramid *before* remarkbox misses the shim. That covers
pyramid's own console scripts — `pserve`, `pshell` — under setuptools>=81. Our
serving path and alembic are unaffected.

If that becomes annoying, the fix is to make the shim resolvable without
importing our package first: ship it as a top-level `pkg_resources` in
site-packages, or drop a `.pth` file that adds `_vendor` at interpreter start.
Not worth doing until someone actually needs `pshell` on a box with a modern
setuptools.

## The shim is permanent, not a bridge

An earlier draft of this ticket said the end state was pyramid dropping
`pkg_resources`, after which `_vendor` could go. Checked, and that is wrong on
the facts:

- **pyramid 2.1 — the current release — still imports it**, in `asset.py` and
  `path.py`, and uses no `importlib.resources` anywhere. We are on 2.0.2, so
  upgrading would not help.
- Pyramid ships slowly (2.0 → 2.1 spans years) with no visible migration, so
  planning around upstream moving is planning around nothing.

So treat `_vendor/pkg_resources` as infrastructure we own and maintain, not a
stopgap. That is the better outcome anyway: it decouples us from setuptools
entirely, which is why setuptools may float freely in our lock.

**Removing it would need every runtime importer to stop**, not just pyramid.
Checked our whole site-packages: pyramid is the only one. `wcwidth`'s mention
is a comment explaining that it *removed* its use; `_pytest` and `nose` are
test-only; `setuptools` and `pip` are the package itself.

**Our shim already covers pyramid 2.1 exactly.** Its full API surface there is
`DefaultProvider`, `register_loader_type`, `resource_exists`,
`resource_filename`, `resource_isdir`, `resource_listdir`, `resource_stream`,
`resource_string` — all eight are implemented. A pyramid upgrade would not
widen the surface today; re-check this list when one lands.
