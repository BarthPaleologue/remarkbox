# T29 — "Held" posts are published: approved=False hides nothing on a default namespace

**Status:** resolved — option 1 shipped 2026-09-13 on fox's call
**Priority:** high
**Source:** zero-sorry audit of our spam subsystem, 2026-09-13

## What is true today

`check_spam` returns `action="held"`, our API sets `node.approved = False`,
our ledger writes a `held` row, and our caller returns HTTP 201. Every one of
those is a success token. None of them is adjudicated by our visibility rule.

`Namespace.can_see_node` (`remarkbox/models/namespace.py:437`):

```python
if self.hide_unless_approved and not node.approved:
    visible = False
```

`hide_unless_approved` defaults to `False` (`namespace.py:103`). On a
default namespace an unapproved node is visible to everyone. Our API thread
reader applies the same gate (`api/views.py:547`), so held posts are served
to embeds and clients alike.

So on a default namespace, a "held" post is:

| what our token says | what actually happens |
|---|---|
| held for moderation | published, same as allowed |
| waits for a human | in no queue: our `pending` view is reachable only when `hide_unless_approved` (`list_nodes.py:120`), and our `spam` view needs `spam_score >= 0.5` |
| an LLM-only hold (score 0.4) | published, unlabelled, unqueued |
| moderators told | only when a `node_event` exists; anonymous surrogate posts have none (`api/views.py:678`) |

Our `(spam)` label (`snippets.j2:82`) and our `spam_nodes` queue both
hard-code `0.5` rather than reading `spam.soft_threshold`.

## Why this matters

Our whole 2026-08-31 relevance work argued that holding is safe because "a
false positive waits for a human instead of silently 403ing a real
comment". Holding is our ceiling for any model verdict for that reason. On a
default namespace the ceiling is a no-op: a correct verdict changes nothing a
reader can see, and a false positive is invisible too, so we cannot learn
from it either.

Our ledger's `held` count therefore measures decisions, not outcomes.

## Options

1. **Make held mean hidden.** `can_see_node` hides any node whose
   `approved is False`, regardless of `hide_unless_approved`; moderators and
   owners still see it. Make our `pending` queue reachable whenever unapproved
   nodes exist. Blast radius: any existing node with `approved = False` on a
   namespace that later turned `hide_unless_approved` off would disappear
   from public view. We cannot count those without a production read.
2. **Hide only spam holds.** Same as 1 but gated on `spam_score is not None`,
   which only our API path sets. Narrower blast radius, one more rule to
   explain.
3. **Rename the token.** Call it `flagged`, keep it published, and fix our
   docstrings and CLAUDE.md so nobody believes a hold protects anyone.

Option 1 is what every docstring already claims we do. Recommend 1, with a
production count of `approved = False AND spam_score IS NULL` nodes first
(via a new admin endpoint, never raw SQL) to size our blast radius.

## What shipped

Option 1. One home for our rule: `Namespace.visibility_filters()` feeds our
API thread reader and every export; `can_see_node`, `page_nodes` and
`visible_roots` hide `approved is False` on every namespace. Our `pending`
queue and its menu link are reachable whenever unapproved nodes exist, and
moderators get approve/deny buttons on a denied node without turning
moderation on. `GET /api/v1/admin/namespaces` now reports
`hide_unless_approved` and `denied_count` per namespace so our blast radius
can be read after deploy instead of guessed before it.

Found on the way: our pending RSS feed compared against `Namespace.feed_key`,
a column that does not exist. Under `hide_unless_approved` it raised; on
every other namespace it served our moderation queue to anyone. It now fails
closed for everyone until a real key exists.

Still hard-coded: `0.5` in our `(spam)` label and `spam_nodes` queue.
